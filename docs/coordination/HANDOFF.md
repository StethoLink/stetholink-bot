- **Sub-step 1, groundwork (done, unit-tested in `tests/backend/orders-core.test.ts`, 14 tests; not wired to any service, route or screen):**
  - **Contracts** `shared/contracts/orders.ts`, `shared/schemas/orders.ts`: `OrderCatalog` is `{ version, items, sets, interactions }`. An item has `id`, `kind` (`lab`, `imaging`, `medication`, `nursing`), `display`, `synonyms`, optional `code` `{ system, code, display? }`, `medication` `{ product, dose, route, frequency, duration? }` (required for a medication, refused for anything else), `matchTerms` (how a chart names that medicine), `groups` (what the interaction rules refer to) and `allergyTerms`. `OrderDraft` holds `mode` (`specific` or `case_based`), the request as written, `lines`, `unmatched`, the cited `clinicalFacts`, `provenance` and a `version`; an `OrderLine` has `basis` (`requested` or `proposed`), `reason`, `evidenceIds`, `flags`, `status` (`pending`, `approved`, `rejected`), `decidedBy`, `acknowledged` and `overrideReason`; the physician's answer is an `OrderDecisionRequest` `{ draftId, expectedVersion, idempotencyKey, decisions[{ lineId, decision, acknowledged?, overrideReason? }] }`.
  - **`core/orders/authoring.ts`:** the model receives the request, age and sex, the visit reason, the chart's facts and, from the catalog, only `id`, `kind`, `display` and `synonyms` of the items and the sets; never a code, a product, a dose, a route, a frequency, allergy words or groups (a test checks the exact text). It answers `{ mode: specific | case_based | unclear, items: [{ itemId, requestedText, reason, evidenceIds }], unmatched }` under a strict schema (an extra field such as a dose makes the whole answer invalid). `validateOrders` keeps an id only if it is in the catalog and only once; a **specific** request keeps only orders whose catalog name or synonym the physician wrote; a **case-based** request may propose an order only with at least one cited *known* chart fact (limited to the order set the request names, at most 12) and keeps the orders the physician also named. It counts what it dropped (`rejected`). The code, product, dose, route and frequency are **not** in what it returns: the service must copy them from the catalog item.
  - **`core/orders/flags.ts`:** `flagsFor(item, otherItemsInTheDraft, { catalog, facts, existing })` returns `allergy`, `allergies_unchecked` (no allergy fact is known, so nothing is claimed), `duplicate_active` (the medicine is in the active medication facts), `duplicate_order` (the same item is already pending or approved in this encounter), `interaction` (the hospital's own `interactions` rule between the item's `groups` and the active medications or the other lines of the draft) and `interactions_unchecked` (the active medications could not be read). StethoLink adds no clinical knowledge of its own. `requiresOverride(flag)` is true for an allergy or a major interaction.
  - **`core/orders/text.ts`:** matching of the physician's words in English and Arabic (case, accents, Arabic marks, alef, ya, ta marbuta, the Arabic article, and the joined Arabic "and": "وأشعة" matches "أشعة").

## Working in the cloud container

- Docker: start the daemon with `nohup dockerd > /tmp/dockerd.log 2>&1 &`. If it refuses with a stale pid, remove `/var/run/docker.pid` and `/var/run/docker.sock` first. Docker Hub sometimes answers 429; wait and retry. Image builds need `--network host --build-arg HTTPS_PROXY=$HTTPS_PROXY`.
- Node's `fetch` needs `NODE_USE_ENV_PROXY=1` to reach outside hosts. `api.openai.com` and `api.elevenlabs.io` have proxy-injected credentials: pass `OPENAI_API_KEY=proxy-injected` (and `ELEVENLABS_API_KEY=proxy-injected`) to scripts that insist on a key.
- The proxy ends every outbound request at 30 seconds; long model calls fail here for that reason only.
- Playwright with Chromium is preinstalled: `NODE_PATH=/opt/node-tools/node_modules`.
- `live-ehr-flow.mts` run by hand needs a production build and a database with TLS, as `run-ci.sh` sets up (`localhost` URL plus `STETHOLINK_DATABASE_CA`); without TLS the launch answers 500. `bash tests/e2e/run-ci.sh` does all of it in about a minute.
- There is no synthetic staging app any more. For browser work without an EHR, run `live-ehr-flow.mts` with `LIVE_E2E_BROWSER=1`, or start the fakes from `tests/e2e/fakes/ehr.mts` and launch through them as that script's `smartLaunch` does. For a real chart use the OpenEMR steps above.

- **Background processes here:** `run_in_background` already backgrounds a command; an `&` inside it makes the finished-notice arrive before the work ends. `next start` leaves a child `next-server` that keeps the port after the parent is killed (`pkill -f next-server`). When this session's long background tasks reached their time limit the Docker daemon and its containers stopped: start the daemon again as above and `docker start` the containers (a published PostgreSQL port changes; OpenEMR's data was still there). Prefer one finite command per background task.
- **Git in a fresh session here:** the checkout may be a detached `HEAD` while the local branch `claude/wizardly-ptolemy-wyp0dh` is old; `git push origin claude/wizardly-ptolemy-wyp0dh` then fails as non-fast-forward. Check `git branch --show-current` first; if it is empty, `git checkout -B claude/wizardly-ptolemy-wyp0dh HEAD` (after `git merge-base --is-ancestor <old local tip> HEAD` says nothing is lost) or push with `git push origin HEAD:claude/wizardly-ptolemy-wyp0dh`.
- **A disposable PostgreSQL for the SQL suites alone (about 20 s):** `docker run -d --name x -p 127.0.0.1::5432 -e POSTGRES_HOST_AUTH_METHOD=trust postgres:17`, then `STETHOLINK_TEST_OWNER_URL=postgres://postgres@127.0.0.1:<port>/postgres node tests/e2e/m3-migrations.mts` applies every migration and runs the suites. A new migration that replaces an old function must re-run that function's old suite after it (see the list in `tests/e2e/m3-migrations.mts`).
- **`postgres.js` and `jsonb`:** pass a value to a `jsonb` parameter with `tx.json(value)`; a string is encoded a second time and never equals the stored JSON.
